# Spike R1 follow-up: choose which Mac displays a client sees

Date: 2026-10-03
Question: The Mac has more displays than the client (3 vs 2 on desktop Windows App, 3 vs 1 on iPad). Can the remote user choose which Mac displays fill which client monitors (for example Mac 1 and 3 on client 1 and 2), with the pointer crossing between them correctly?
Build / version of IronRDP: crates.io `ironrdp-server` 0.13.0 / `ironrdp-acceptor` 0.10.0 (pinned). Acceptor re-checked on `master` 2026-10-03 (last commit to `connection.rs`: 2026-09-30). Display control, server and connector re-checked on `master` 2026-10-04, plus release PR #2067.
What we ran: source inspection of mrdpd and IronRDP. No live session.
Evidence (logs, PDUs, links):

- An RDP client never sees the server's displays. It reports its own monitors (GCC at connect, `DisplayControlMonitorLayout` over RDPEDISP after connect) and the server decides what fills each one. Choosing Mac displays is a server-side mapping; stock clients work unchanged. A Windows host is different: its RDP session ignores the physical monitors and builds a desktop shaped like the client's, so there is nothing to choose there.
- `SCKFrameSource` captures `content.displays.first`. `DisplayMap` already maps RDP pixels to any single display's global origin and Retina scale (`DisplayMapTests`). Showing a different single display is a capture-selection change; the input math exists.
- `RdpServerDisplay::request_layout` (0.13.0) can carry N monitors, but `DisplayControlServer::start` advertises `DisplayControlCapabilities::new(1, 3840, 2400)`, so clients send at most one over RDPEDISP. The spec's "implemented" for T2-MON-02 was wrong for more than one monitor (corrected 2026-10-04).
- The acceptor answers with one `PRIMARY` monitor in `MonitorLayoutPdu` (`MonitorLayoutSend` in `connection.rs`), unchanged on `master`. It already sets `EXTENDED_CLIENT_DATA_SUPPORTED`, so clients may send their GCC monitor list; it is parsed into `gcc_blocks.monitor` and ignored. Two client monitors hit the same blocker as R1 (T2-MON-01).
- 2026-10-04, IronRDP `master`: #1918 (merged 2026-09-28) adds `RdpServerDisplay::monitor_count()`, which sets the RDPEDISP ceiling. Connector 0.10.0 sends `monitor: None`; on `master` it sends `Config.monitor_layout` and records the server's answer in `ConnectionResult.monitor_layout`, so a headless two-monitor E2E is possible.
- 2026-10-04: release PR #2067 (open since 2026-10-01) bumps `ironrdp-server` 0.13.0 → 0.14.0, acceptor and connector 0.10.0 → 0.11.0, displaycontrol 0.8.0 → 0.9.0. Breaking changes since 0.13.0 include #1245 (`ServerResult` display traits), #1691 (keyboard metadata) and #1787 (Large Pointer). No open upstream issue or PR covers the connect-time N-monitor layout.
- `CGEventInputSink` posts absolute positions. A pointer crossing the client's seam from monitor 1 to monitor 2 warps from Mac display 1 to Mac display 3 and never crosses display 2.

Answer: **Feasible.** Model: a table of client monitor rect (RDP pixels) → Mac display ID + fit (scale, letterbox offset).

- Frames: one `SCStream` per *selected* display, scaled by SCK to its client monitor's size (letterboxed if the aspect differs), composited at that monitor's origin with dirty rects translated.
- Input: hit-test the RDP point against the client monitor rects and apply that entry's `DisplayMap` plus the inverse fit. Points in gaps snap to the nearest monitor.
- Default (owner, 2026-10-03): Mac displays fill client monitors in left-to-right order (A→1, B→2); extra Mac displays start hidden. One client monitor (owner, 2026-10-04): the main display.
- Picker (owner direction, 2026-10-03): a translucent tab at top center, about 10% of the monitor's width, like Jump Desktop's toolbar. Click it, pick a Mac display from tiles laid out like the Mac, then click the outlined client monitor it should go on. Proposed, not decided: picking a display already shown on another monitor swaps the two; with one client monitor the pick applies directly; keep the outline step, or apply the pick to the monitor whose tab was clicked.
- Picker mechanics: mrdpd draws the tab, panel and outlines onto each captured frame before `push_frame`. That is a new step: today ScreenCaptureKit draws the cursor (`showsCursor`), so the overlay would sit on top of it, and mrdpd must draw its own pointer while the pointer is over the overlay (client-side cursor, T2-GFX-01, would remove that). The overlay's rect joins the dirty rects whenever it changes. An `InputSink` decorator consumes clicks on the tab, in the panel and during the outline step. Switching does not renegotiate: client monitor sizes stay fixed; only the capture feeding that monitor and its fit change. Before the picker exists, the same mapping can come from mrdpd config or CLI. A custom client is not required.
- Gotchas: windows, dialogs and notifications that open on an unselected display are invisible remotely. With "Displays have separate Spaces" off, the menu bar and Dock live only on the main display, so leaving it out hides them; the picker should warn. Dragging a window across the seam can leave part of it on the hidden display. The tab covers the quietest part of the macOS menu bar (app menus left, status items right), but clicks there go to the tab, not the Mac.

Effect on spec / M9 / M10: T2-MON-03 assumed one stream per display and T2-MON-04 covers a client with *more* monitors than the Mac; nothing covered *fewer*. 2026-10-04: added T1-MON-02, T2-MON-05 and T2-MON-06, narrowed T2-MON-03 to captured displays, and corrected T2-MON-02 ([ADR 0006](../adr/0006-mac-display-mapping.md)). The ABI needs an engine → Swift layout callback; M8 (`T1-MON-01`) needs the same callback for iPad resize, so it lands once, there. `push_frame` can stay one composited frame. Choosing the single display for the iPad needs no IronRDP or ABI change; fit-to-iPad scaling is M8.
Follow-up (upstream issue, ADR, OUT-row): ADR 0006. The single-display pick is T1 (T1-MON-02, M6 follow-up). Spike R15 checks the tab position before the picker is built. After the M6 gate: move to IronRDP 0.14, then file the upstream issue and PR for the connect-time layout (owner OK first). The two-monitor mapping stays behind the M6 gate and R1.
