# Spike R2: MS-RDPEI touch server

Date: 2026-08-20
Question: Can mrdpd take iPad touch (MS-RDPEI) from IronRDP **today**, or only mouse/keyboard FastPath?
Build / version of IronRDP: `ironrdp-rdpei` **0.1.x** (crate exists on `master`); `ironrdp-server` **0.13.0**.
What we ran: source inspection of `crates/ironrdp-rdpei/src/server.rs` and `crates/ironrdp-server/src/server.rs` (`attach_channels`).
Evidence (logs, PDUs, links):

- `ironrdp-rdpei` implements a real **server** DVC processor: `RdpeiServer` + `RdpeiHandler` (`cs_ready`, `touch`, `pen`, `dismiss_hovering`), SC_READY / CS_READY, touch and pen PDUs. README: MS-RDPEI Input Virtual Channel Extension.
- `ironrdp-server` **does not attach** that processor. `attach_channels` wires AInput, DisplayControl, Echo, and optional EGFX. Grep for `rdpei` / `Rdpei` in `ironrdp-server` is empty.
- There is no `with_rdpei_factory` on `RdpServerBuilder`. Adding RDPEI means an upstream PR (extra `.with_dynamic_channel(RdpeiServer::…)` on the per-connection DVC) or a fork. A `StaticChannelFactory` cannot inject a dynamic channel into the already-built DVC without that hook.
- Client-side RDPEI in IronRDP is further along (`ironrdp-session`, `ironrdp-agent` touch-tap). That does not help our **server**.

Answer: **PDU + server processor exist; the engine skeleton does not use them.** T2-IN-03 is **implement via upstream PR** (or a thin local patch to `attach_channels`), not OUT. Until that lands, T1 keeps mouse-wheel as the iPad scroll fallback (already in ABI v1 `MrdpdMouseEvent.wheel`). Pen stays OUT-IN-01.
Effect on spec / M9 / M10: No change to T1. T2-IN-03 remains after M6 + spike; this file is the spike. Do not add ABI touch functions in v1 (ISP).
Follow-up: Upstream PR “attach `RdpeiServer` as a DVC and forward `TouchEventPdu` to `RdpServerInputHandler` (or a new trait)”. Map two-finger scroll to wheel in Swift `InputSink` once events exist. No ADR now.
